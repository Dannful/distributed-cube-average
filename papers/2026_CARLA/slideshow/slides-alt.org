* Motivation & Contributions
** Halo Exchange & the Masking Problem
- Halo exchange
  - Commonly applied in iterative stencil computations across HPC nodes.
- Each MPI process keeps a /ghost-cell/ layer
  - It attempts to *overlap* halo transfers with interior computation
  - Also known as communication masking

#+latex: \vfill\pause

- Effective *masking* depends on the interplay of:
  - halo size,
  - problem size,
  - partitioning topology,
  - interconnection bandwidth.
- Important to characterize such an interplay
  - But it requires sweeping those parameters \to costly
  - A very diverse hardware \to rarely available

** The Cost of Real Hardware

- Real HPC infrastructure \to expensive, time-limited, imutable
  - "Would 100Gbps InfiniBand change masking?"
    - Unanswerable on a 1Gbps cluster.
  - Topology studies (e.g. 64 nodes)
    - Impossible with only 5 nodes.

#+latex: \vfill\pause

- Alternatives [according to Jain 1991]:
  - traditional experimental \to impossible
  - analytical modeling \to misses cache, PCIe, OS noise
  - simulation \to _our choice_.

** SimGrid / SMPI

Unmodified MPI code runs on top a virtual platform
- Intercepts MPI calls and simulates them with contention
  - Network parameters from systematic *calibration*.
- Computation runs natively on the host \to a /calibrated emulation/
  - Compute timings observed /in situ/

#+latex: \vfill\pause

SimGrid/SMPI
- Proven for communication-intensive benchmarks (e.g. HPL).
- Published uses focus on collectives, scheduling, load balancing
  - There is no ghost cell masking viability study

** Gap & Contributions

*Gap*
- To our knowledge, SimGrid/SMPI has never been used to evaluate
  *ghost cell masking effectiveness* in MPI stencil applications
- Fletcher RTM seismic application (realistic, GPU-heavy,
  bw-sensitive)

#+latex: \vfill\pause

- *Contributions*:
  1. Distributed MPI Fletcher (3D decomp., async ghost cells)
     - Numerically validated
  2. Calibrated SimGrid/SMPI framework [with a 15% error margin]
  3. An evaluation of masking across *three host configurations*
     - CPU-only + two GPU clusters

* Methods & Materials
** Static Domain Partitioning                                            :noexport:
#+ATTR_LATEX: :center t :width \linewidth
[[file:../img/comm_cost.png]]

- Uniform stencil work $\Rightarrow$ balanced load $\Rightarrow$ *static*
  decomposition suffices.
- *Blocks* minimize the surface-to-volume ratio: slices grow as
  $2(P-1)L^2$, blocks only as $6(\sqrt[3]{P}-1)L^2$.
- Built with =MPI_Dims_create= + =MPI_Cart_create=.
- *Caveat*: prime $P$ degenerates to a $\{P,1,1\}$ slice layout ---
  avoid prime rank counts.

** Ghost Cells: The Five-Step Overlap
Within each time step:
1. Post non-blocking receives (=MPI_Irecv=) for incoming halos.
2. Compute the *boundary strips* (with previous-iteration data).
3. Dispatch them asynchronously (=MPI_Isend=).
4. Compute the *interior* while halos are in transit.
5. =MPI_Waitall=, insert halos, swap wavefield buffers.

#+BEGIN_EXPORT latex
\vfill\pause
#+END_EXPORT
*Masking works only when interior computation outlasts the halo
transfer.* Otherwise step 5 stalls and communication dominates.

** The Fletcher RTM Application

- *Reverse Time Migration*
  - Method to reconstruct subsurface images
  - Cross-correlates forward- and backward-propagated wavefields
- *Fletcher's method*
  - Pseudo-acoustic wave equations for *anisotropic* (TTI) media

#+latex: \pause\vfill
- Very computationally intensive \to *GPU-friendly*
  - Ideal to stress ghost cell masking
    - Fast compute makes it harder to attain communication masking

#+latex: \pause\vfill

*** Our Fletcher RTM implementation MPI+CUDA
:PROPERTIES:
:BEAMER_env: block
:END:
- Flexible 3D data decomposition [using MPI helper ops]
- *CUDA backend*
  - wavefields stay in device memory throughout the run
  - only halo buffers cross the PCIe bus via 3D strided copies
- *Numerical validation* vs. single-node reference:
  - OpenMP: =SHA-256= bitwise-identical (30 configs, \(32^3\)--\(512^3\));
  - CUDA: per-element delta \(<\) $10^{-15}$.
- With SimGrid/SMPI: MPI is simulated, CUDA is truly executed
  
* Results
** Masking Effectiveness Metric

- Trace =MPI_Waitall= ops with an in-house fast tracer [akypuera]
  - Comm. ratio = Aggregate comm. time / aggregate makespan

- *Masking Effectiveness* = 1 - communication ratio
  - Closer to 1 means a better communication hiding

** Design of Experiments

Full factorial [from Jain 1991] sweep over three factors
- *problem size*: $64^3$, $128^3$, $256^3$, $512^3$ [facets]
- *number of hosts*: 4, 8, 16, 27, 64 [colors]
- *network bandwidth*: 1, 2.5, 10, 25, 50, 100 Gbps [X-axis]
  - Fixed \(22\,\mu\mathrm{s}\) latency
  
The application
- 1000 iterations per run [main loop]
- No replication [as emulations are quite stable]

Three host models (single node each, calibrated on =poti=):
- =cei=: 2\times Xeon Silver 4116 (CPU-only)
- =poti=: RTX 4070
- =tupi=: RTX 4090

** CPU Cluster =cei=: Masking is Free
#+begin_center
The higher the measurements, the better the masking effectiveness.
#+end_center

#+ATTR_LATEX: :center t :width \linewidth
[[file:../img/cei-masking.png]]

- Below 100Mbps: masking \(<\) 0.30 (communication-bound).
- Past *1Gbps* it jumps: \(512^3\)/8 hosts \(\approx\) *0.94*;
  \(256^3\)/8 hosts \(>\) 0.89.

#+latex: \vfill\pause

Takeaway
- Low Xeon FP throughput lets computation fill the gaps
  - Good masking, essentially free

** GPU Cluster =poti=: The Net Bottleneck
#+begin_center
The higher the measurements, the better the masking effectiveness.
#+end_center

#+ATTR_LATEX: :center t :width \linewidth
[[file:../img/poti-masking.png]]

- At *1Gbps*: masking stalls near *0.25*, independent of problem size.
  - The RTX 4070 outruns the Gigabit link
  - =MPI_Waitall= dominates every iteration    
- Recovery begins at *10Gbps* (\(512^3\)/4 hosts reaches 0.97)

#+latex: \vfill\pause

Takeaway
- GPU generates a network bottleneck
  - Must have a network with certain bandwidth

** GPU Cluster =tupi=: A Scaling Anomaly
#+begin_center
The higher the measurements, the better the masking effectiveness.
#+end_center

#+ATTR_LATEX: :center t :width 0.95\linewidth
[[file:../img/tupi-masking.png]]

- As =poti=, but shifted higher \to RTX 4090 is much faster
- *Anomaly*: from $256^3$ to $512^3$, masking improves *only* with many
  hosts (27, 64); few hosts (4--16) get *worse*.

#+latex: \vfill\pause
Takeaway
- Volume/surface dynamics: small subdomains are surface-dominated at
  $256^3$ and only amortize communication at $512^3$.
