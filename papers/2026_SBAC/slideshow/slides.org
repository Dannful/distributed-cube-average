* Motivation & Contributions
** Halo Exchange in Distributed Stencils
- Halo exchange is the foundational technique for distributing
  iterative stencil computations across HPC nodes.
- Each MPI process keeps a /ghost-cell/ layer --- a local copy of its
  neighbors' boundary data --- so it can *overlap* those transfers
  with its own interior computation.
- Whether this overlap genuinely *masks* communication depends on three
  interacting factors: the problem size, the partitioning topology,
  and the interconnection bandwidth.
- With small domains or slow networks, communication dominates; with
  large domains and fast networks, computation can fully hide the
  transfers.

** The Fletcher RTM Application
- Reverse Time Migration (RTM) reconstructs subsurface images by
  cross-correlating seismic wavefields propagated forward and backward
  in time.
- Fletcher's method solves the pseudo-acoustic wave equations that
  model how those waves travel through direction-dependent
  (anisotropic, TTI) rock.
- At every time step it couples a pressure field $p$ with an auxiliary
  field $q$ using an eighth-order finite-difference stencil.
- The method is computationally intensive and memory-bound, which is
  exactly why it benefits so strongly from *GPU acceleration*.

** The Gap in the Literature
- Every prior GPU-accelerated Fletcher implementation runs on a
  *single node*, using shared memory or peer-to-peer GPU links.
- This single-node limit caps both the computational throughput and
  the GPU memory available as problems grow.
- The underlying distributed-stencil techniques --- 3D block
  decomposition, asynchronous overlap, SimGrid calibration --- are
  already well established.
- However, *no prior work has distributed the Fletcher method across
  multiple cluster nodes* via MPI with ghost-cell halo exchange.
- This leaves open how partitioning topology and network bandwidth
  /together/ determine how effectively communication can be overlapped.

** Contributions
1. We present a *distributed MPI implementation* of Fletcher that uses
   3D block decomposition and asynchronous ghost-cell communication,
   validated numerically against the single-node reference.
2. We add *GPU acceleration via CUDA*, keeping the wavefields resident
   in device memory while preserving the same overlap strategy as the
   CPU version.
3. We *evaluate on real HPC clusters* and show that bandwidth and
   topology jointly govern masking, from \(\approx\)20% on a 1Gbps GPU
   cluster to over 87% on a 10Gbps CPU cluster.
4. We *use emulation* (SimGrid SMPI) to estimate the network capacity
   required to hide communication completely.

* Methods & Materials
** Static Domain Partitioning
#+ATTR_LATEX: :center t :width 0.72\linewidth
[[file:../img/comm_cost.png]]

- The stencil does identical work everywhere, so the load is balanced
  and a *static* decomposition is enough.
- The domain can be split into *slices* $\{P,1,1\}$, *columns*, or
  *blocks*.
- *Blocks* win by minimizing the surface-to-volume ratio: slice
  boundaries grow as $2(P-1)L^2$, blocks only as $6(\sqrt[3]{P}-1)L^2$.
- We build the grid with =MPI_Dims_create= and =MPI_Cart_create=.
- *Caveat:* when $P$ is prime, the grid collapses back to a slice
  layout.

** Ghost Cells: The Five-Step Overlap
Within each time step, every process performs five steps:
1. It posts non-blocking receives (=MPI_Irecv=) for the halos it
   expects from its neighbors.
2. It computes the *boundary strips* from the previous iteration and
   sends them asynchronously (=MPI_Isend=).
3. While those messages travel, it computes the *interior* of its
   subdomain.
4. It calls =MPI_Waitall= and inserts the halos that have arrived.
5. Finally, it swaps the wavefield buffers for the next step.

\vspace{0.4em}
#+END_EXPORT
This only masks communication when the interior computation takes
longer than the halo transfer. If the network is the bottleneck, step 4
stalls and communication dominates.

** Distributed Fletcher RTM Design
- The application follows a *coordinator--worker* model on a 3D
  Cartesian topology.
- The coordinator (rank 0) partitions the domain and sends only
  *compact metadata* --- never the wavefield data itself.
- Each worker allocates and initializes its own sub-volume
  ($p_{\text{past}}, p_{\text{curr}}, q_{\text{past}}, q_{\text{curr}}$),
  so there is *no central memory bottleneck*.
- Output is collected in a streaming fashion, avoiding a second
  bottleneck at the end of the run.
- Every process exchanges halos with its 26 neighbors, for both
  wavefield components $p$ and $q$.
- On multi-GPU nodes, each process is bound to a GPU according to its
  rank.

** Numerical Validation
- We compare our output against the *single-node reference*
  implementation.
- With the *OpenMP backend*, =SHA-256= checksums over 30 configurations
  (1--6 workers, sizes $32^3$ to $512^3$) are *bitwise-identical*.
- With the *CUDA backend*, per-element differences stay within
  $10^{-15}$ --- near-bitwise agreement, as expected from normal
  CPU/GPU rounding.

** Evaluation Methodology
- We use two clusters of the PCAD platform, chosen for their
  contrasting compute-to-communication balance.
- The */cei/* CPU cluster has six nodes (two Xeon Silver 4116 each) on
  a *10Gbit* network.
- The */poti/* GPU cluster has five nodes (RTX 4070, 12GB) on a
  *1Gbps* network.
- We trace every run with *akypuera*, convert the traces with
  *PajeNG*, and analyze them in R.
- We report performance in *MSamples/s*, the metric used for the
  reference Fletcher code.
- We use *SimGrid SMPI* to simulate 10 and 100Gbps networks beyond our
  hardware, emulating the real kernel and calibrating against /poti/
  (error \(\le\) 15--17%).

* Results
** Reading the Charts
- All charts come from *PajeNG* traces that record each rank's MPI
  operations over time.
- A synthetic *Compute* state fills the gaps between MPI events, and it
  includes the PCIe copies to and from the GPU.
- Each experiment is shown two ways: a *Gantt chart* (rank vs. time,
  one rectangle per event) and a *load chart* (the run split into 100
  bins, stacking the Compute and =MPI_Waitall= fractions).
- The rule for reading them is simple: *a higher compute load means
  communication is better hidden.*

#+ATTR_LATEX: :options {0.44\textwidth}
#+BEGIN_column
- There is a *dramatic gap* between the 5-worker and 8-worker
  configurations.
- At $512^3$, 8 workers reach *8309* MSamples/s (10Gbps) and *9374*
  (100Gbps).
- The 5-worker runs stall at *3030 / 3215*, *below* the single-node
  baseline of *3870*.
- With 5 workers, distributing the work actually gives *negative
  speedup*.
#+END_column
#+END_columns

** Why? Prime Process Counts
- Because 5 is prime, =MPI_Dims_create= is forced into a $\{5,1,1\}$
  *slice* layout, whereas 8 factors cleanly into $\{2,2,2\}$ *blocks*.
- For a $512^3$ domain with stencil thickness 4, the 5-worker slices
  send \(\approx\)8MB faces, about *64MB per iteration*.
- The 8-worker blocks send \(\approx\)2MB faces plus small edges and
  corners, only about *25MB per iteration*.
- Blocks therefore cut the per-worker volume by roughly *2.5\times*,
  even though each worker now talks to 7 neighbors instead of 2.
- Raising the bandwidth tenfold barely helps the slice case (+6%), so
  its real bottleneck is *large-message protocol paths and fixed
  per-transfer costs*, not raw bandwidth.
- In short, *a prime process count hurts as much as a slow network.*

* Conclusion
** Conclusion
- We observed two sharply contrasting regimes.
- On the *CPU*, modest floating-point speed gives near-perfect masking,
  reaching 87% compute load at $512^3$.
- On the *GPU*, the RTX 4070 makes the 1Gbps network the bottleneck,
  holding the compute load near *20%* regardless of problem size.
- Calibrated SimGrid reveals a *smooth transition* as bandwidth grows:
  \(\approx\)20% at 1Gbps, \(\approx\)75--80% at 10Gbps, and
  \(\approx\)85--90% at 100Gbps.
- The main lesson is that *bandwidth and partitioning topology together
  determine* how well ghost-cell communication is hidden.
- Prime process counts force slice layouts and can even produce
  *negative speedup*, so they should be avoided.

** Future Work
- We plan to run on the *Santos Dumont* supercomputer, which offers a

- We intend to add *HIP kernels* so the code also targets AMD GPUs.
